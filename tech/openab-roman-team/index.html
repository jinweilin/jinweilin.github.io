OpenAB 與羅馬團隊：我們如何打造多 Agent 開發組織

OpenAB 是道路與驛站；不同 AI Agent，則是各司其職的專業團隊。 金霸研究編輯部 · 2026 年 9 月 13 日 · 約 7 分鐘閱讀

OpenAB 不是一個 AI 模型，而是把不同 AI Agent、聊天平台與工作流程串起來的 Agent 調度平台。它讓團隊可以在熟悉的聊天介面提出需求，同時保留專業分工、工作階段與執行邊界。

OpenAB 是什麼？

OpenAB 全名是 Open Agent Broker。官方將它定位為輕量、安全且雲端原生的 ACP harness：平台端負責接收訊息、調度 Session 與管理通道，再透過 Agent Client Protocol（ACP）把工作交給 Claude Code、Codex、Grok、Devin、Gemini、Antigravity 等相容的 Agent runtime。

OpenAB 的價值不在於取代模型，而在於把模型變成可持續運作的服務。它處理多平台訊息、Thread 多輪對話、Session pool、Agent 互相協作、檔案與圖片傳遞、排程工作，以及 Kubernetes 部署所需的持久化與生命週期管理。

我們的羅馬帝國開發軍團

我們沒有讓同一個 Agent 同時定義需求、寫程式、測試，再自己宣布滿分。羅馬軍團採用角色分工與責任分離，把產品開發拆成一條可以檢查、退回與驗收的流程。

  1. 格拉古：需求訪談確認真正要解決的問題，整理需求與驗收標準。
  2. 凱撒：規劃與派工判斷方向、拆解 Issues，協調後續執行順序。
  3. 維特魯威：工程實作撰寫程式、測試修改，並提交可供審查的 PR。
  4. 加圖：品質把關從功能、邊界條件與 E2E 行為挑錯，不讓「能跑」冒充「能用」。
  5. 阿格里帕：部署與維運負責發布、服務驗證、監控，以及必要時的回退。
  6. 格拉古：最終驗收回到最初需求，確認成果真的解決使用者問題。

刻意使用不同後端也有風險分散的效果：如果所有角色都依賴同一套模型，它們可能共享相似盲點；透過異質模型與明確驗收標準，可以降低「大家很有共識，但一起看錯」的機率。

眾議院：討論與執行分開

除了開發軍團，我們也設置「眾議院」作為顧問與政策討論場域。凱撒與格拉古常駐，加圖及阿格里帕依主題提供 QA 或維運意見。討論可以形成表決與 SWOT 分析，但決議只是建議，不會自動派工或部署；意見無法收斂時，由金霸做最後裁定。

眾議院負責把事情吵清楚，軍團負責把事情做清楚。把顧問場域與執行場域分開，可以避免一邊討論方向，一邊意外改動正式環境。

羅馬軍團以外的專業單位

整個 OpenAB 艦隊不只有開發團隊。金小霸與金二霸屬於金霸直屬的個人側；另有旅遊規劃、社群內容、每日視覺、台股研究及圖像工作室等獨立團隊。各自有明確入口、權限與交付流程，不需要所有問題都送進開發軍團。

真正的價值：組織設計，而不只是 Agent 數量

多 Agent 系統最容易掉進「角色很多，看起來很熱鬧」的陷阱。如果沒有清楚的責任邊界、交付格式、權限控制與最終驗收，增加 Agent 只會增加溝通成本。

我們目前的方向，是讓 OpenAB 負責穩定的通訊與調度，讓每個 Agent 專注自己的專業角色，再透過 Git、PR、測試與部署紀錄留下可以追蹤的成果。

OpenAB 是帝國的道路、驛站與通訊系統；Agent 是各司其職的官員。真正重要的不是官員有多少，而是權責是否清楚、命令是否可追蹤、結果是否有人驗收。
