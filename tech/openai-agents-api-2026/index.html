Agents API：
模型正在變成基礎設施

從架構、成本、資安與平台策略，解析 OpenAI 將 Codex agent harness 開放給開發者之後，企業真正得到什麼，又必須承擔什麼。

分析：金霸研究編輯部　·　2026 年 9 月 13 日　·　約 10 分鐘閱讀

Executive conclusion

先講結論

Agents API 真正要取代的，不是某一個聊天 API，而是企業自行拼裝的 Agent orchestration、session state、context management 與 sandbox infrastructure。

  • 最大機會：縮短 Agent 從原型走向生產環境的距離。
  • 最大挑戰：成本、資安、治理與平台依賴沒有消失，只是換了管理位置。
  • 策略建議：先在可讀、可逆、低權限且成果容易驗證的流程試點。

2026 年 9 月 10 日，OpenAI 發表公開測試版 Agents API。表面上，它是一套快速建立 AI Agent 的 API；更深層的意義是 OpenAI 不再只供應模型，而是開始提供一套可長時間運行、管理狀態、調用工具及協調多個代理人的託管式執行層。[1]

Agents API 究竟提供了什麼？

Agents API 將支撐 Codex 的 agent harness 開放給開發者。OpenAI 管理 session、orchestration、context compaction 與 recovery；開發者指定模型、指令、工具、MCP 服務及執行環境。官方將核心抽象分成 Agent、Environment、Session、Events and Items。[2]

Agent 不再只是「呼叫模型、收到答案」，而是一個能持續工作、保存進度、等待工具、接受中途引導，甚至拆解任務的執行單位。

產業競爭的重心，正在從模型端點移向可持續運作的 Agent Runtime。

1. 開發抽象層往上移

過去團隊要自行處理對話狀態、工具迴圈、上下文壓縮、非同步任務、錯誤恢復、sandbox 生命週期、多 Agent 分工與執行紀錄。Agents API 把很大一部分交給 OpenAI 維護。[2]

這像企業從自架伺服器走向雲端：工程工作不會消失，但團隊能把精力移到業務流程、資料品質、工具契約與評估方法。

2. 推理層與執行環境分離

開發者可以不使用環境、採 OpenAI 託管 sandbox，或連接 self-hosted environment。若需要內網或自有運算，executor 可從企業環境以 outbound WebSocket 連回 Agents API。[3][4]

但自架仍要負責 provisioning、重新連線、關機、檔案保存，以及 session 與 compute 的對應。雲端把麻煩搬家，不是把麻煩火化。

3. 多 Agent 開始產品化

Agents API 原生支援 coordinator 將工作交給 subagents。官方文件顯示，預設最多同時執行六個 subagents，不包含 coordinator；但 subagents 共享環境與檔案系統，而且目前不支援 function tools。[5]

任務若能清楚拆分，可平行檢查部署紀錄、程式碼與依賴服務；若拆分不良，則可能增加重複工作、衝突、延遲與 token 成本。

4. 工具不再一次塞進上下文

Tool Search 允許模型需要時才載入工具定義，避免所有 schema 一次佔據 context，並盡量保留 prompt cache。[6] Programmatic Tool Calling 則讓 Agent 在隔離的 V8 runtime 中以程式調用工具，先過濾、排序、去重或彙整，再把精簡結果送回模型。涉及核准或高影響操作時，仍適合直接工具調用。[7]

帶來的機會

降低基礎建設門檻

中小團隊不必從零打造 session persistence、工具迴圈、compaction、recovery 與 subagent orchestration。

垂直 Agent 加速

競爭差異將從模型選擇轉向資料、工具、權限、評估方法與產業流程。

混合部署新市場

VPC sandbox、credential broker、MCP gateway 與治理平台，都可能形成新的基礎設施市場。

長任務更可營運

自動 compaction、session continuation、webhooks 與 recovery，減少上下文耗盡與斷線負擔。

可觀測性標準化

Session logs、events、turn、subagent 身分與 token usage，讓團隊能追查問題來源。[8]

面臨的挑戰

Public beta 風險

介面與最佳實務仍可能快速調整。現階段適合受控 pilot，不適合直接接管核心交易。[1]

成本不只是單次 token

API 本身不另收平台費，但模型、subagents、重試、工具、sandbox 及第三方服務都會計費。應衡量可靠完成一項任務的總成本。[8]

執行權限擴大攻擊面

Agent-generated code 能存取環境允許的檔案、憑證與網路。隔離、egress allowlist、最小權限與 credential broker 不能省。[9]

平台依賴

Codex harness 雖開源，但 session、vault、事件與 tracing 仍是平台服務。業務規則與評估資料不宜全部綁在供應商設定。

可觀測不等於可治理

公開測試版尚未提供 tracing configuration 或外部 trace exporter；詳細 trace 主要透過 Dashboard 查看。[10]

案例數字不能直接外推

官方文中的成本與失敗率改善來自早期客戶 testimonial，並非統一條件下的獨立 benchmark。[1]

Management checklist

企業導入前，先回答五個問題

  1. Agent 判斷錯誤時，最壞可以改動什麼？
  2. 哪些工具只讀，哪些寫入動作必須人工核准？
  3. 如何衡量成功率、人工介入率、總成本與延遲？
  4. Context compaction 後，限制與證據是否仍完整？
  5. 若 API 或環境供應商變更，哪些業務邏輯可以帶走？
Final verdict

最終結論：機會與挑戰

Agents API 標誌著 AI 產業從 Model as a Service 走向 Agent Runtime as a Service。

機會在於開發週期縮短、小型團隊也能建立長時間多工具工作流，並帶動垂直產業、MCP、sandbox 與治理市場。挑戰則是 public beta 的變動、多 Agent 成本放大、執行權限帶來的資安風險，以及平台依賴與稽核整合。

建議先從可讀、可逆、低權限、成果容易驗證的流程試點，建立人工基準線，再用成功率、總成本與維護負擔決定是否擴大。

這場競爭最後不只比誰的 Agent 跑得快，而是比誰知道它什麼時候不該跑。
