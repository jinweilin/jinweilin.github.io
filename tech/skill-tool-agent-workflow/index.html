Skill 是方法，Tool 是能力

從多人旅行規劃的痛點出發，用一個助理案例看懂 AI 工作流程怎麼分工，以及為什麼最後的確認仍該由人負責。金霸研究編輯部 · 2026 年 10 月 6 日 · 約 8 分鐘閱讀

多人旅行時，難的不只是在腦中想出安排；還得把每個人的想法收在一起、排出可討論的順序與移動方式，再讓大家確認。對我來說，這份燒腦的整合工作常集中在一個人身上。要讓 AI 助理分擔，先分清兩件事：它依什麼方法工作，以及它能使用哪些外部能力。

Go 醬是我為這類規劃痛點構想的旅行助理。本文只用它作為脫敏概念案例，討論工作如何拆分，不呈現實際系統設定或實作規格。

Skill 安排工作怎麼走；Tool 提供助理能使用的能力；誰有權做決定，仍要另外確認。

把一團忙亂拆成幾種不同工作

我想解決的不是「沒有人會找景點」，而是規劃者常得同時記住需求、順序、移動限制和大家的回覆。先把任務拆開，助理要做的就不再是一團模糊的「幫我們排行程」，而是幾件較清楚的工作：補齊缺少的條件、整理可選方案、把資訊排成可閱讀的草稿，再交給同行者確認。

這個例子不是共享旅行攻略，也不是 Go 醬的完整技術說明；它只是用來看清 AI 助理的工作分工。這裡的 Skill 和 Tool 是概念層次的說法，不包含任何特定系統的內部設定或規格。

Skill 與 Tool，分別回答不同問題

Skill：這類工作要怎麼做？

把可重複的方法整理成指引：先問哪些必要條件、如何檢查安排是否合理、怎麼標出未知，以及什麼時候應停下來請人確認。它讓流程不必每次都從零開始。

Tool：助理能做哪些操作？

提供與外部資訊或系統互動的能力。例如在一個抽象的旅行助理中，工具可能用來查詢公開資訊、讀取獲准使用的資料，或保存已確認的內容。能呼叫某項工具，不代表任何情境都應呼叫它。

用生活化的比喻，Skill 像一份工作手冊，Tool 像桌上可用的器具。手冊告訴你步驟與檢查點；器具讓你能完成某些操作。但器具本身不會決定誰有權拍板，手冊也不能單靠文字把不恰當的權限變合理。

不同平台對 Skill、工具與 Agent 的命名和實作可能不一樣。以 OpenAI 公開文件為例，Agent Skills 被描述為可重用的指示與支援檔案；Agent 的定義也把 instructions 和 tools 分開配置。這是理解概念的一個參照，不是所有平台都必須採用的固定分類。[OpenAI：Agent Skills；OpenAI：定義 Agent]

從想法到可確認的草稿：四步拆工作

1. 拆出子步驟

把需求蒐集、整理選項、提出草稿、確認與後續更新分開看，別用一個「全自動」按鈕概括整件事。

2. 先問資格與代表權

助理是在替誰處理事情？它能代表誰做哪種決定？如果授權不清楚，就先補問或停止。

3. 判斷值得自動化嗎

估計重複整理帶來的節省，再扣掉工具建置、查核、例外處理與維護成本；能做不等於值得做。

4. 把人放在適當的確認點

助理可整理出版本供大家檢視；涉及不同人的取捨、尚未確認的資訊或會產生外部承諾的操作，就應保留清楚的人類確認。

這四步也說明了為什麼 Skill、Tool 不是權限制度的替代品。Skill 可以提醒助理按流程工作，Tool 可以讓它查詢或修改資料；至於某次操作是否被授權、是否值得做、是否必須等人批准，仍是另一層要明確設計的問題。

好的助理不是代替大家決定

在旅行規劃這個例子裡，助理的價值可以是把散落的想法整理成大家看得懂的草稿，讓意見比較容易被看見，也更容易討論。它不該擅自替同行者決定誰的偏好優先；當條件不清楚或意見衝突時，先呈現差異、再請人選擇，比假裝有唯一正解可靠。

設計檢查：每加入一項 Tool，都問它會讀取什麼、可能改變什麼，以及誰批准這個操作。把「查詢」、「草擬」與「對外執行」分開，才看得見真正需要人把關的位置。

把整理交出去，把共同決定留下來

這篇想分享的不是某一套神奇提示詞，而是設計助理時可以先問的三個問題：這份工作的方法能否重複使用？完成它需要哪些外部能力？最後哪些判斷仍屬於人？

當這三件事分清楚，AI 就不必在「什麼都不做」和「什麼都自動做」之間二選一。它可以接手繁瑣整理，讓草稿更早出現；而人保留確認權，讓重要選擇仍由真正要一起生活在結果裡的人完成。

讓助理承擔整理，不等於把人的選擇也交出去。
