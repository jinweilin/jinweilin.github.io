原來做一個網站也可以這麼簡單

當「放網站的地方」免費了、「組頁面的工作」自動化了，做網站剩下的難處，已經和十年前完全不一樣。這篇拆解內容型網站的新做法：三步流程、preview 先行、後台被換掉，和沒變簡單的那四件事。金霸研究編輯部 · 2026 年 11 月 9 日 · 約 7 分鐘閱讀
對「內容型」網站——公司介紹、產品型錄、規格文件、詢價——做網站的流程已經簡單到一個程度：內容整理成結構化檔案，放進 GitHub 私有 repo，push 上去，Cloudflare Pages 自動把網站建好、發佈到全球節點，託管月費 0 元，只剩域名年費。簡單的不是「隨便做做」，而是以前最花錢、最花時間的兩層——主機託管和逐頁製作——分別被平台免費額度和自動化拆掉了。但先講清楚：這只適用於內容型網站，需要金流、會員、即時庫存的「系統型」網站不在此列，後面會劃界線。

先說以前為什麼「不簡單」

很多人對做網站的印象停在這裡：買主機、裝 CMS、做版型、一個頁面一個頁面刻，完工之後每年還要付主機費和維護費，隔幾年系統老了、版本不支援了，整站打掉重做。

這個印象在當年是真的。傳統動態網站是一台一直在跑的伺服器程式：有資料庫、有後台登入頁、有一堆外掛，每個零件都要更新、要修補、要有人盯。貴的不是某一個零件，是「整套系統要持續照顧」這件事本身。費用有一大半，是在為這套複雜度買單。

所以問題來了：如果一個網站的內容根本不需要即時運算——產品型錄不會因為有人來看就變內容，規格 PDF 下載一萬次還是同一份檔案——那為什麼要養一台伺服器在那裡跑？

現在的做法，只有三步

第一步：內容先變成檔案，而不是頁面

關鍵觀念轉換在這裡：不要一頁一頁做網站，先把內容整理成結構化資料——每個產品一筆紀錄，欄位是型號、分類、簡介、圖片、規格檔；頁面交給程式照範本自動組出來。

一家 B2B 廠商有兩三百項產品很常見，聽起來很多，但人要整理的只是兩三百筆資料，幾百個頁面是程式一次生成的。分類頁、品牌頁、搜尋索引也一樣，全部是資料餵範本的結果。日後加一個品牌、換首頁輪播圖、調整欄位，改的是資料和範本，不是幾百個頁面逐一手工修。

這一層以前要靠 CMS 後台和資料庫撐，現在一份結構化檔案就夠了——因為加上 AI 協作之後，把既有網站清點、轉成結構化資料的速度，和過去人工逐頁搬運已經不是同一個量級。

第二步：GitHub 私有 repo，當倉庫兼保險箱

組好的網站原始檔和內容資料，放在 GitHub 的私有 repo 裡。GitHub 免費版就提供數量不限的私有 repo 和協作者，對一個企業官網來說，這一格的成本是 0 元（官方定價頁，2026-11-09 查核）。

repo 還有兩個附帶價值：一是版本紀錄，每次改了什麼、誰改的、什麼時候改的，天然留痕，要回溯或還原都有依據；二是備份，網站的全部資產就是一包檔案，不綁在某台主機、某間廠商的後台裡，公司換誰接手都帶得走。

第三步：Cloudflare Pages，push 一下就上線

託管交給 Cloudflare Pages：repo 一有新 commit，它就自動建置、自動部署，網站由 Cloudflare 的全球網路送到訪客面前，HTTPS 憑證自動處理，DDoS 緩解是內建的。

免費版的額度，對企業官網來說寬到幾乎感覺不到天花板：每月 500 次建置、每個網站 20,000 個檔案、單一檔案上限 25 MiB、每個專案可綁 100 個自訂網域，靜態內容的請求與頻寬不限量（Cloudflare 官方限制文件，2026-11-09 查核）。一個久久更新一次、幾百到幾千個檔案的官網，離任何一條線都很遠。託管月費就這樣變成 0 元，經常性成本只剩域名年費（金額視註冊商與網域後綴而定）。

上線流程還有一個關鍵設計：先預覽，確認後才轉正式。改動先開在分支或 Pull Request 上，Cloudflare Pages 會自動產生一個專屬的預覽網址，版面、內容、連結都先在預覽站上驗一遍；預覽不會動到正式站和自訂網域，確認沒問題，再把分支合併進正式分支，才算對外發佈。改錯了，正式站毫髮無傷；要回退，也只是回到上一個版本。這道「先看過、再放行」的關卡，正是這套做法敢把流程做得這麼簡單的底氣。

三步連起來：改資料、push、自動上線。沒有主機要登入，沒有後台要維護，沒有外掛要更新。

那後台呢？被換掉了，不是被省掉

傳統官網一定要有一個後台：登入、編輯、按發佈。這套做法最常被問的就是——那後台去哪了？

答案是：後台的四個功能——編輯、審核、發佈、紀錄——都還在，只是拆給三個東西接手。內容本體是 repo 裡的資料檔；審核靠 GitHub 的 Pull Request 流程，改動先開 PR、先看預覽，核准了才合併；紀錄是版本歷史，誰在什麼時候改了什麼，天然留痕。至於實際動手改的那個人，現在可以是 AI：GitHub 和 AI 工具整合之後，你用講的就好——「新增這三項產品、換掉首頁那張圖」——AI 直接改資料、開 PR、附上預覽網址，你要做的只剩下看預覽和點核准。

所以後台不是被省掉，是被換成一套更輕的介面：repo 加 PR 加 AI 對話。附帶的好處在資安：沒有對外開放的後台登入頁，就少了一整類被攻擊的入口，下一節會講。

界線也要講：公司裡如果有多位非技術同仁要天天自己上稿、改文章，熟悉的後台畫面還是有它的價值，CMS 不會因為這套做法就消失。但對「久久改一次、改的人固定」的企業官網，養一整套後台系統來服務一年幾次的編輯，成本和風險都划不來——換成 AI 代勞加 PR 審核，反而更省事。

簡單背後，資安的風險搬了家

靜態網站有一個結構性的安全優勢：沒有資料庫、沒有後台登入頁、沒有外掛，傳統 CMS 最常見的那一整類漏洞——弱密碼登入、過期外掛被植入、資料庫注入——攻擊面整類消失，不需要每月追著安全性更新跑。

但風險沒有消失，是搬家了。新的大門是帳號和域名：GitHub 和 Cloudflare 帳號一旦被盜，網站內容和流量導向就一起被拿走；域名註冊和 DNS 控制權在誰手上，決定公司對自己官網還剩多少主導權——實務上最常見的狀況，是域名當年由廠商代註冊、DNS 放在廠商的帳號裡，公司要搬家時才發現鑰匙不在自己手上。

所以這套做法的資安功課很明確：帳號一律開在公司自己名下、強制雙重驗證、權限只給需要的人，域名和 DNS 的歸屬在動工之前先談清楚。把這幾件事做對，靜態架構的安全性是結構上就成立的，不靠事後補丁。

先講界線：不是每個網站都適合這樣做

這套做法有它的適用範圍，硬套會出事：

  • 適合：公司與品牌官網、產品型錄與規格站、文件與下載中心、活動與形象頁——內容會更新，但更新頻率以週或月計，而且不需要訪客帳號。
  • 不適合：電商購物車與金流、會員系統、即時庫存與訂單查詢、需要後台讓非技術人員隨時自行編輯的內容平台。這類「系統型」網站需要的是會運算的後端，該用電商平台或 CMS 的地方就用它們。

兩條路線是並存的，不是谁淘汰誰。判斷方法只有一個問題：你的網站主要是「給人看的內容」，還是「替人辦事的系統」？前者用靜態做法，簡單又便宜；後者乖乖付系統的錢，天經地義。

那還有什麼是不簡單的

把話說完整，免得這篇變成業配式的樂觀：託管和組頁變簡單了，但有四件事沒有變簡單，也不會因為工具進步就消失——事實上，架構越簡單，這四件事在整個案子裡佔的比重反而越高：

  1. 設計與版面：看起來專業、手機上好讀、資訊找得到，這是設計功力，不是平台送的。
  2. 內容與雙語校對：產品資料對不對、翻譯通不通順、型號有沒有打錯，工具只能加速，正確性還是人負責。
  3. 遷移驗證：舊網址逐筆比對、QR Code 和外部連結不能斷，這是最枯燥也最不能錯的一段。
  4. 帳號治理與交接：帳號開在誰名下、權限怎麼給、人事異動怎麼交接——這是管理問題，技術幫不上忙，但出事時最貴。

換句話說，專業的價值沒有消失，是搬了位置：從「會架主機、會維護系統」，移到「內容正確、遷移可靠、治理清楚、有人負責」。對不想碰技術的企業主來說，要買的也正是後面這一段，不是主機本身。

結尾：先問你的網站是內容，還是系統

做網站變簡單，是真的，但簡單的是特定的那一類。把問題問對，後面全部迎刃而解：你的官網如果九成是給人看的內容——介紹、型錄、規格、聯絡——那它今天就可以用「資料加工廠流水線」的方式重做一次，月費歸零、維護歸零，工夫花在內容驗證和帳號治理上。如果它是替人辦事的系統，那就不是這篇文章的題目，預算該花在系統品質上，不要省錯地方。

工具會繼續進步，但這個分類不會過時：內容歸內容，系統歸系統。分清楚，網站這件事就簡單了。

一句話總結：先分清你的網站是「給人看的內容」還是「替人辦事的系統」——是內容，流程已經簡單到只剩改資料、看預覽、點核准；是系統，就把預算花在系統品質上。
